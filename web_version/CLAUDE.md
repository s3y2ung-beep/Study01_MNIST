# web_version/CLAUDE.md

손글씨 숫자 인식의 웹(자바스크립트) 버전. 이 폴더의 파일을 다룰 때 루트 CLAUDE.md에 더해 읽는다.

## 원칙

- 외부 라이브러리 없이 순수 자바스크립트(ES 모듈)로 추론한다. 빌드 도구도 쓰지 않는다.
- GitHub Pages에 정적 파일 그대로 올라가야 한다.
- 기능은 데스크톱 버전과 같다(280x280 그림판, 손을 떼면 인식, 상위 3개 후보, 지우기). 웹에서는 터치 입력만 더했다.

## 파일

| 파일 | 역할 |
|---|---|
| `index.html`, `스타일.css` | 앱 화면 |
| `앱.js` | 시작점. 모델 적재, 인식, 결과 표시 |
| `그림판.js` | 마우스/터치 그리기, 흰 글씨/검은 바탕 밝기 배열 추출 |
| `전처리.js` | `preprocess.py`의 3단계 전처리 |
| `모델.js` | `model.py` 순전파 재작성, 가중치 적재 |
| `검증.html` | 파이썬 결과와 대조하는 검증 페이지 |
| `가중치.bin`, `가중치정보.json` | `desktop_version/가중치내보내기.py`가 만든 가중치 |
| `검증데이터.json` | `desktop_version/검증데이터만들기.py`가 만든 정답 데이터 (깃에 넣지 않음) |

## 로컬 실행

ES 모듈과 `fetch`를 쓰므로 `index.html`을 더블클릭(`file://`)해서는 동작하지 않는다. 웹 서버로 연다.

```
cd web_version
py -m http.server 8000      # 맥: python3 -m http.server 8000
```

그다음 브라우저에서 `http://localhost:8000/` (앱), `http://localhost:8000/검증.html` (검증).

## 배포

저장소 루트의 `.github/workflows/pages.yml`이 main 브랜치에 푸시될 때마다 이 폴더만 GitHub Pages로 올린다.
저장소 Settings → Pages → Source가 GitHub Actions여야 한다 (`gh api repos/{owner}/{repo}/pages`의 `build_type`이 `workflow`).

## 가중치.bin 형식

- 텐서 8개(합성곱1, 합성곱2, 전결합1, 전결합2 각각 weight, bias)를 float32 리틀 엔디언으로 이어 붙인 것. 파라미터 421,642개, 1,686,568바이트.
- 각 텐서의 이름, 형상, 시작 위치(원소 단위)는 `가중치정보.json`에 있다. 형상과 원소 순서는 파이토치와 같다(합성곱: 출력, 입력, 세로, 가로 / 전결합: 출력, 입력).
- 정규화 상수도 `가중치정보.json`에서 읽는다. 자바스크립트에 숫자를 직접 적지 않는다.

## 파이썬과 맞춰야 할 지점

- 층 구조: `모델.js`의 `예측()`은 `model.py`의 `forward()`와 같은 순서여야 한다. 풀링 뒤 평탄화 순서는 채널, 행, 열.
- 전처리: `전처리.js`는 `preprocess.py`와 같은 3단계. 다른 점은 축소 방식 하나(PIL LANCZOS 대신 면적 평균). 검증에서 정확도가 충분해 Lanczos는 구현하지 않았다.
- 반올림: 양쪽 모두 `floor(x + 0.5)`.
- 면적 평균 축소에서 칸 끝 좌표는 원본 크기로 잘라 둔다. 예를 들어 `19 * (21 / 19)`는 `21.000000000000004`가 되어 배열 밖을 읽는다.

## 검증 절차

1. `desktop_version/`에서 `py 가중치내보내기.py`, `py 검증데이터만들기.py`
2. 이 폴더에서 웹 서버를 띄우고 `검증.html`을 연다.
3. 기준: 순전파 확률 최대 절대차 1e-4 이하, 200장 중 97% 이상 정답, 전처리 실패 0장. 현재 실측은 5.41e-7, 98.0%(196장), 0장.
4. 검증 데이터 200장 중 170장은 10배 최근접 확대, 30장은 임의 배율, 부드러운 가장자리, 임의 위치다. 검증 통과는 "시험해 본 범위 안에서 옳다"는 뜻이므로 마지막에 직접 그려서 확인한다.

## ONNX를 쓰지 않은 이유

ONNX Runtime Web은 외부 라이브러리라 요구 사항에 어긋난다. 모델이 작아(층 4개) 순전파를 직접 쓰는 편이 간단하고, 계산 과정을 코드로 볼 수 있어 교육용으로도 낫다.
